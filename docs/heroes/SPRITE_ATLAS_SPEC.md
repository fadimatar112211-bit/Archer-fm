# مواصفات Sprite Sheet وAtlas — Archer FM

الحالة: معيار إنتاج أولي معتمد للتجربة، وليس قياساً نهائياً قبل اختبار الأداء  
التاريخ: 2026-11-14

## 1. الهدف والنطاق
توحيد تصدير شخصيات 2.5D من نموذج 3D Chibi إلى إطارات PNG شفافة قابلة للتحميل والعرض داخل محرك اللعبة. هذه المواصفات لا تختار محرك اللعبة ولا تفترض وجود نموذج 3D أو ملفات إنتاج نهائية حالياً.

## 2. بنية الملفات المقترحة
```
assets/
  heroes/
    ranger/
      source/                 # ملفات المصدر ثلاثية الأبعاد؛ لا تُحمّل وقت اللعب
      renders/
        idle/
        walk/
        attack/
        death/
      atlases/
        ranger_atlas.png
        ranger_atlas.json
      previews/
```

- أسماء الملفات lowercase وبـsnake_case، والمعرّف الثابت للبطل `ranger`.
- ملفات المصدر وملفات المعاينة لا تدخل حزمة التشغيل.
- لا تُستبدل أصول SVG القديمة قبل اعتماد البديل واختباره.

## 3. الإطار والكاميرا ونقطة الارتكاز
- كل إطار مربع؛ نقطة البداية التجريبية: 256×256 بكسل.
- يُختبر أيضاً 192×192 إذا حافظ على وضوح silhouette، و320×320 عند الحاجة للتفاصيل. لا يُحسم المقاس النهائي إلا بعد القياس على جهاز مستهدف.
- خلفية PNG شفافة RGBA؛ يمنع تضمين checkerboard أو لون خلفية أو ظلال مسطحة كبيرة.
- كاميرا Orthographic ثابتة، مع اتجاه/زاوية وإضاءة وخامات موحدة لكل مجموعة.
- موضع القدمين/نقطة تماس الأرض هو pivot؛ يحفظ كإحداثيات normalized داخل الإطار، ويجب أن يبقى ثابتاً بين الإطارات والاتجاهات.
- لا تقص أي جزء من القوس أو السهام أو العباءة. يسمح بهوامش شفافة ثابتة.
- كل الإطارات بنفس أبعاد canvas وبنفس مقياس الشخصية.

## 4. تنظيم الاتجاهات والحركات
المجلدات/المفاتيح القياسية:
- الاتجاهات: `s`, `sw`, `w`, `nw`, `n`, `ne`, `e`, `se`.
- الحالات: `idle`, `walk`, `attack`, `death`.
- أسماء الإطارات: `ranger_<state>_<direction>_<index padded to 3 digits>.png`.
- مثال: `ranger_walk_sw_000.png`.
- النموذج الأولي الأول يقتصر على اتجاه مائل واحد وidle/walk فقط؛ لا تُنتج بقية الاتجاهات قبل نجاح اختبار الجودة والأداء.

## 5. توقيت الحركة وأحداث الأنيميشن
- مدة الإطار تحفظ بالميلي ثانية في manifest، ولا تُستنتج من اسم الملف.
- idle وwalk حلقات loop؛ attack وdeath غير متكررتين افتراضياً.
- حركة attack تحتوي حدثاً واحداً باسم `projectile_release` في إطار الإطلاق. محرك القتال وحده ينشئ السهم؛ حدث الأنيميشن يرسل إشارة ولا ينشئ مقذوفاً بنفسه.
- يمكن إضافة أحداث مثل `footstep` لاحقاً، لكنها تجميلية ولا تغيّر حالة اللعب.
- death ينتهي بحالة نهائية ثابتة ولا يعيد الشخصية إلى الوقوف.

## 6. أطلس الصور
- ترتيب الإطارات في atlas بواسطة أداة packing قابلة لإعادة الإنتاج، مع JSON يحدد rectangle لكل frame.
- تفعيل padding لا يقل عن 2px حول كل إطار لتجنب texture bleeding، مع extrusion للحواف إن كانت أداة التصدير تدعمه.
- لا نفترض أن كل الحالات/الاتجاهات ستوضع في صورة واحدة؛ يمكن تقسيم الأطلس حسب البطل أو الحركة إذا كان ذلك أفضل للذاكرة.
- لا تعتمد أبعاد texture تتجاوز حدود الأجهزة المستهدفة؛ افحص maximum texture size على أجهزة الاختبار.
- لا تُستخدم صور JPEG بسبب الشفافية. PNG هو المصدر المرجعي؛ يمكن لاحقاً تجربة صيغة GPU مضغوطة بعد اختيار المحرك ودعم الأجهزة.

## 7. عقد manifest JSON
يحتوي الملف على:
- `schema_version`
- `hero_id`
- `frame_size`
- `pivot` بقيم normalized من 0 إلى 1
- `atlases` ومسار الصورة
- `animations` ولكل حركة: loop، frame_duration_ms، ordered frames
- `events` اختيارية مرتبطة بإطار محدد
- `direction` لكل مجموعة إطارات

مثال هيكلي:
```json
{
  "schema_version": 1,
  "hero_id": "ranger",
  "frame_size": { "width": 256, "height": 256 },
  "pivot": { "x": 0.5, "y": 0.86 },
  "atlases": [
    {
      "id": "ranger_prototype",
      "image": "ranger_atlas.png",
      "meta": "ranger_atlas.json"
    }
  ],
  "animations": {
    "idle_sw": {
      "loop": true,
      "frame_duration_ms": 160,
      "frames": ["ranger_idle_sw_000", "ranger_idle_sw_001"]
    },
    "walk_sw": {
      "loop": true,
      "frame_duration_ms": 100,
      "frames": ["ranger_walk_sw_000", "ranger_walk_sw_001"]
    },
    "attack_sw": {
      "loop": false,
      "frame_duration_ms": 75,
      "frames": [],
      "events": [
        { "frame": 0, "name": "projectile_release" }
      ]
    },
    "death_sw": {
      "loop": false,
      "frame_duration_ms": 120,
      "frames": []
    }
  }
}
```
هذا مثال عقد بيانات فقط؛ أسماء الإطارات والأزمنة الفعلية تُملأ بعد إنتاج الإطارات وقياسها.

## 8. فحوصات قبول الأصول
يجب أن ينجح كل تصدير في الفحوصات التالية:
1. كل إطار PNG صالح وRGBA وبالأبعاد الموحدة.
2. لا توجد خلفية معتمة أو checkerboard مدمج.
3. pivot ثابت، ولا توجد قفزات موضعية غير مقصودة بين الإطارات.
4. لا يوجد قص لأي جزء من الشخصية أو السلاح.
5. ترتيب frames في manifest يطابق أسماء الصور وترتيب الحركة.
6. loop idle/walk بلا قفزة مرئية.
7. حدث إطلاق السهم يحدث مرة واحدة فقط في attack.
8. death لا يعيد التشغيل تلقائياً.
9. تسجيل الحجم الإجمالي للأطلس والذاكرة التقريبية، ثم مقارنة 192/256/320.
10. معاينة الحركة على خلفية فاتحة وداكنة وعلى مقياس العرض الفعلي داخل اللعبة.

## 9. خطة النموذج التجريبي
- إنتاج نموذج 3D واحد للرامي، اتجاه مائل واحد.
- إخراج idle وwalk فقط، مع 6–8 إطارات أولية لكل حركة كعينة اختبار لا كعدد نهائي.
- اختبار 192 و256 و320 بكسل.
- قياس وضوح الشخصية، ثبات pivot، حجم الملفات، واستهلاك الذاكرة/الأداء.
- اعتماد إعداد واحد بعد المقارنة؛ بعدها فقط نوسع إلى الاتجاهات والحركات الأخرى.

## 10. حدود هذه المرحلة
لا يوجد حالياً في المستودع محرك لعبة أو عارض Sprite Atlas أو نموذج 3D نهائي. لذلك لا ندّعي وجود تشغيل داخل اللعبة أو اختبار Android في هذه المرحلة. اختيار محرك اللعبة يبقى قراراً منفصلاً ويجب حسمه قبل كتابة runtime loader.
